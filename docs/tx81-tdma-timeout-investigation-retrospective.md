# TX81 TDMA Timeout 排查复盘：从整包告警到单指令超时门限

整理日期：2026-09-21。本文复盘这次TDMA故障调查中的证据、判断变化和方法教训，供后续编译器与板端调试参考。
硬件事实及版本依据以[故障定位记录](tx81-tdma-fault-localization.md)为准，后续修复状态以
[任务进度](../tasks/progress.md)为准。本文没有新增实卡实验。

## 1. 最终定位到了什么

**已定位的复现中，编译器生成的一条小颗粒GatherScatter持续执行过久，触发了LSU watchdog。
当前板卡的LSU_TIMEOUT寄存器只保留低16位，原值`0xffff`已经是这个配置字段能保留的最大值。**

GatherScatter，下面简称GS，是一条根据地址、步长和迭代参数重复搬运数据的指令。
本次问题出在一条GS内部大量重复4字节搬运；CPU并没有为每个元素发射一条GS。
这里的限制是执行时长门限，不能把65,535直接当作允许的最大迭代次数。

最终证据来自同一条GS的实卡对照：输入、地址、实际SDK packet和执行顺序保持相同，只改变timeout门限。
门限为65,535时正常；降低到16,383后，在执行计数增量约16,597时观察到TDMA fatal。
两次最终都完成了相同的数据搬运，完整执行计数增量都是33,358。

这确认了该复现的触发机制，也确认不能通过向这个寄存器写入更大的值解决问题。
**定位完成不等于生产修复完成**：长GS的生成方式、紧密连续发射和原attention程序仍需修改与验收。
其它历史永久卡死、后续清理失败、原路径早期CT状态也没有被一并归为同一个原因。
详见[最终位宽与因果证据](data/board-performance/tdma-timeout-width-causal-results-20260921.json)。

## 2. 为什么最初很难判断

问题最早表现为连续板测过程中的`LSU TDMA Timeout`，其中一次发生在历史对照包的Tile 2。
随后当前attention包也出现同类告警，部分执行还能返回正确结果，另一些现场又出现completion或资源清理超时。
这些现象同时出现，很容易把“最初的硬件异常”和“异常后的后果”混成一个问题。

当时有几条合理但未经证实的假设：连续运行后硬件资源没有释放、runtime退出路径不同、
搬运参数越界或截断、前面的算术异常影响后续搬运，以及某条指令遇到了未公开的硬件限制。
仅靠再跑一次完整attention，通常只能再得到一条timeout日志，无法在这些假设之间做选择。

缺少的也不只是一本寄存器手册。实际可见资料存在三个具体缺口：

- SDK给出了GS字段和部分PMU寄存器地址，却没有完整说明watchdog的有效位、计时和重载条件。
- 已安装AP驱动的TDMA handler只报告错误、打印Tile编号并更新计数，没有保存故障指令PC或packet。
- 安装包里的旧源码、测试程序与实际运行二进制并不处处一致。例如旧源码对某个EID的命名与实际handler不同。

因此需要先确认“现在运行的到底是什么”，再沿真实二进制补观测点。
文件版本、实际handler和输入有限性等初步检查见[安装包与固件审计](data/board-performance/tdma-firmware-localization-20260920.json)。

## 3. 排查怎样逐步收敛

### 3.1 从日志确认告警来源，同时承认日志没有提供故障指令

检查安装包、已安装runtime、AP模块和Kcore/Score固件，核对文件摘要；
对带符号与DWARF的AP模块反汇编，恢复中断分派表及TDMA handler调用关系。

实际路径确认了：stream fatal的bit 12对应TDMA，handler上报EID `0x0D00C005`。
但该handler没有读取故障packet、PC或队列现场。因此“日志显示Tile 2 TDMA超时”只能定位到Tile和执行单元，
不能回答究竟是哪条GS出了问题。日志中的`need to reset chip`也只是文本，不等于已经执行了reset。

这一步的价值是确定采集缺口，避免继续指望现有日志提供它从未记录过的信息。

### 3.2 用新boot复现，降低对跨调用残留的怀疑

在用户重启后，只运行当前准备好的case，并确认系统级设备占用。
后来取得了“本boot首个计算也发生TDMA”的结果，说明连续运行多个case并不是这一复现的必要条件。
按厂商正常退出处理后仍有告警，也说明恢复厂商清理本身不足以避免它。

这没有证明所有资源管理都正确，但把问题从“必须有上一次调用留下的状态”推进到了“这一次调用内部也能触发”。
后续清理超时发生在TDMA之后，不能倒过来当作初始TDMA的原因。

### 3.3 从PMU观测升级到原程序的实际指令记录

最初增加host侧只读PMU采样，记录异常状态、TDMA计数、last-command和timeout配置。
这能看到告警前后的变化，却无法可靠地把计数映射回程序指令：计数并非已证明的退休序号，
last-command的编码和更新时间也没有完整定义。拿一个计数减去固定常数来猜fault ordinal，不能形成证据。

随后在原target LLVM、CRT和SDK发射路径上补充诊断记录：

- 标记静态调用site、动态packet序号、Tile、worker和engine。
- 记录实际送入SDK issuer的packet字节及发射前后状态。
- 将有界ring放到独立DDR输出，并通过当前固件实际导出的日志接口保留故障附近片段。
- 把首次CT/CSR状态单独保存；继续追踪，直到真正的stream TDMA bit 12出现才冻结ring。

最后一项修正很关键。早版采集器遇到任意异常状态就冻结，实际先抓到了CT `0x800`，漏掉了稍后的TDMA。
“采到了一个异常”与“采到了要调查的异常”并不是一回事。

这一轮把原attention现场缩到了四条命令：

```text
行最大值GS广播 → SubVV → Exp → 后继GS
```

此时已有实际发射参数，但仍有两条TDMA，不能把最后发射的命令直接当成故障命令。
采集方案和四命令窗口见[原路径采集准备](data/board-performance/tdma-original-trace-preparation-20260921.json)
及[故障区间分析](data/board-performance/tdma-causal-matrix-20260921.json)。

### 3.4 把四命令窗口缩成一条GS

接下来没有继续反复运行整包，而是提前准备了一组可区分假设的诊断case：
搬运基线、不同单条规模、同总量的等价拆分、大颗粒搬运，以及必要时才使用的计算依赖和fill分支。
每项都有新生成的合法输入、独立expected、实际ELF/SDK字段检查和no-card结果；异常即停止，不临场重试。

原Tile 4广播的参数是：

```text
inner bytes       = 4
source strides    = [0, 4, 0]
destination strides = [4, 256, 65536]
iterations        = [64, 256, 4]
```

它把256个不同的F32行最大值广播到目标布局，可用下面的伪代码描述地址语义：

```text
for chunk in 0..3:
    for row in 0..255:
        for lane in 0..63:
            dst[chunk * 16384 + row * 64 + lane] = row_max[row]
```

这是**一条GS内部的64×256×4次搬运**，总量256 KiB。数字来自该次实际编译产物，
不是编译器固定采用的tile尺寸。它广播的是不同的行最大值，也不是整块填同一个`-inf`。

实际串行执行到第7项时取得了决定性的缩小结果：

| 实验 | TDMA execution增量 | 结果 |
| --- | ---: | --- |
| 只初始化和回读，无GS | 0 | 健康 |
| 同256 KiB、inner=1024的大颗粒搬运 | 3,445 | 健康，但排列不同，使用自己的oracle |
| 单条1,024次，inner=4 | 2,125 | 健康 |
| 单条4,096次，inner=4 | 8,365 | 健康 |
| 完整65,536次拆成16条，各4,096次 | 133,840 | 健康，相同逐点地址访问序列 |
| 单条16,384次，inner=4 | 33,358 | 健康 |
| 单条32,768次，inner=4 | 首次fatal时65,863 | TDMA fatal，停批 |

这些数字是寄存器计数原值，不是微秒。最后一项没有CT、Sub、Exp或第二条TDMA，
因此它的TDMA异常可以明确归到这唯一一条GS。无需先获得硬件fault PC，也能完成单指令定位。

这组结果还排除了几种解释：32,768次已经失败，问题不要求迭代次数达到65,536；
拆分后累计执行计数超过65,535仍正常，问题也不是PMU累计总量达到这个数。
指令颗粒度和单条持续时间成为主要线索。
完整参数与原始结果见[单GS隔离实测](data/board-performance/tdma-single-gs-isolation-20260921.json)。

### 3.5 从厂商测试找门限入口，但不把软件类型当成硬件位宽

在SDK中查到了Tile-local PMU地址：`LSU_TIMEOUT`位于`0x59028c`，
`NE_CT_TIMEOUT`位于`0x590288`。只读快照显示16个Tile的前者均为`0xffff`，后者均为`0xffffffff`。

继续离线分析厂商SLT里的`ncc_ras_test.bin`，发现RDMA/WDMA超时测试会用32-bit store向LSU地址写10，
任务结束后写`0xffffffff`。这证明厂商测试确实通过设置门限制造超时，却仍不能证明寄存器能保留全部32位。

还有两个需要避免误读的细节。其一，旧SLT的TDMA测试检查bit 12，却调用了另一个地址的setter；
V1.6和V1.8相关代码一致，不能直接照搬到当前板卡。其二，当前Kcore的`set_pmu_reg`使用16-bit store，
但已确认的调用用于PMU clear/enable，没有证明它设置了LSU timeout，不能据此指认软件截断为根因。
函数和版本证据见[门限寄存器审计](data/board-performance/tdma-timeout-register-audit-20260921.json)。

至此必须分开三个对象：

| 对象 | 已有证据 | 含义 |
| --- | --- | --- |
| GS每维iteration | SDK字段和issuer为32位 | 描述搬运重复次数 |
| TDMA execution累计计数 | 低/高两个寄存器组成64位，实测超过65,535 | 记录执行工作，不是配置门限 |
| LSU timeout | 现场读到`0xffff`，当时有效位宽尚未知 | 决定超时条件的配置字段 |

数值接近是调查线索，只有针对配置和行为的实验才能确认因果。

### 3.6 写入、读回、恢复：确认寄存器只保留低16位

在用户授权后，先准备完所有分支及恢复检查，再通知重启。
位宽实验只改Tile 4的LSU_TIMEOUT，使用实际32-bit `sw`，避开Kcore那个会截取16位的helper。
初始化搬运已完成，测试窗口没有GS在途；每种位型写入后立即读回并恢复原值。

| 写入 | 读回 |
| --- | --- |
| `0xffffffff` | `0x0000ffff` |
| `0xaaaaaaaa` | `0x0000aaaa` |
| `0x55555555` | `0x00005555` |
| `0x0001ffff` | `0x0000ffff` |
| `0x8000ffff` | `0x0000ffff` |

互补位型证明低16位确实可改，高位没有保留；各次恢复都读回原来的`0xffff`。
因此，当前这块卡的这个寄存器访问路径不能配置大于65,535的值。
这一步确认的是配置字段的可读写位，还需要下一步确认它对GS行为的作用。

### 3.7 只改变门限：把相关性变成因果证据

按位宽结果选择已准备的低16位分支，对同一条16,384次GS做两个case：

| 唯一改变的timeout值 | GS实际行为 |
| --- | --- |
| `0xffff`＝65,535 | 正常完成，execution增量33,358 |
| `0x3fff`＝16,383 | execution增量16,597时首次观测TDMA fatal；最终仍完成，完整增量33,358 |

两组输入、SDK packet、同步和采样相同。为只改变GS的条件，实验顺序固定为：

```text
RDMA初始化 → 厂商join → 保存/设置/读回timeout
→ 单条GS → 终端采样 → 厂商join → 恢复/读回原值
→ WDMA完整回读 → 厂商join及正常退出
```

这处GS后的完成边界只用于诊断，两组相同，没有加入生产同步。
因此可以排除“降低门限把输入/输出DMA也弄超时”的混淆：故障时RDMA已经完成，WDMA尚未发射，
CT count、CSR exception和PMU exception raw也都为0。

第三项出现预期的TDMA fatal后立即停批。三项都完成2 MiB逐byte输出、10,240 guard bytes检查和16 Tile退出，
原配置由设备侧恢复，再由host只读核对全部16个Tile。故障case依然按不健康处理。
故障后stream已经读0，host journal也没有新告警，但设备DDR快照和EP日志明确抓到了窗口内的fatal。

**同一条指令仅改变门限便改变结果，确认了LSU timeout对该TDMA故障的因果作用。**
16,597是顺序采样首次看到异常时的值，不是精确到某一拍的触发值。
完整准备与实测分别见[实验准备](data/board-performance/tdma-timeout-experiment-preparation-20260921.json)
和[最终结果](data/board-performance/tdma-timeout-width-causal-results-20260921.json)。

## 4. 走过的弯路，也要如实留下

资料不完整增加了难度，但排查拖长并不全是资料的问题。我们自己的实现和调查方式也增加了干扰。

| 弯路或错误 | 为什么影响判断 | 后来的处理与教训 |
| --- | --- | --- |
| 用重复跑整包、历史包代替缩小故障 | 再次得到timeout，仍不知道哪条指令触发；历史性能已有记录，额外运行会增加恢复成本 | 转向当前case的最小触发窗口，历史日志只作审计 |
| 曾用`_Exit`绕过厂商全局析构 | 引入了额外生命周期差异，却没有证明它能解决TDMA | 按用户要求统一回到厂商清理；正常退出仍复现，清理与初始故障分开分析 |
| 把mask同值铺块和普通broadcast混在一起 | `-inf`同值填充低效，不代表行最大值广播也能换成同值fill | 同值填充改为整块`XorVV + AddVS`；不同源值的普通broadcast仍须保持语义，后续正是在这里定位到长GS |
| CRT自行把浮点fill改成同宽整数format | 为保留位型而改变了算术dtype，SDK字段检查与成本测试还跟着错误规则自洽 | 删除这项自行增加的规则，实际dtype照常传递；标量字段用整数承载位型不等于整数运算 |
| 日志函数只核对SDK声明，没核对固件导出 | 引入未导出的`tx8_kernel_printf`，设备loader失败，浪费了一轮诊断机会 | 对照实际固件RTMSymTab检查最终ELF全部导入符号；函数能加载和日志能收到也分别验证 |
| 首个异常就冻结采集器 | 早期CT状态挡住了后面的TDMA证据 | 分别保存首次CT状态与TDMA触发窗口，按目标异常冻结 |
| 从PMU计数或最近命令直接猜故障指令 | 观察顺序、发射顺序和硬件完成顺序不能混用 | 原程序动态packet记录先缩区间，再由单条GS独立复现确定指令 |

其中，浮点format替换是我们实现引入的软件错误，不是用户要求，也没有厂商指令定义支持。
修正后原路径仍出现早期F32状态和TDMA；最终无CT的单GS复现又证明，早期CT并非本次TDMA触发的必要前置。
应修正这个错误，但不能把“找到了一个bug”直接写成“找到了正在调查的根因”。
相关边界保留在[fill格式修正证据](data/board-performance/fill-dtype-correction-20260921.json)。

用户持续要求先定位具体指令、分析计数上限、把case准备齐再重启，是这次调查收敛的重要推动。
对需要人工恢复的设备，下一轮重启应换来能区分假设的新证据，而不是重复同一条告警。

## 5. 可以复用的排查方法

**先写清楚要区分的假设，再决定采什么、跑什么。** 每个实验至少要回答：改变了什么、保持了什么、
看哪个信号、两种结果分别说明什么，以及触发故障后是否还能拿到必要证据。
本次最终的门限对照能奏效，正是因为这些问题在重启之前就准备好了。

一套适合类似问题的顺序是：

1. 固定实际运行身份：输入、package/ELF、runtime、driver、firmware及boot，保留摘要和真实命令。
2. 分开首次故障、后续状态和清理结果，先查现有日志究竟记录了什么。
3. 对缺失信息加最小采集：实际packet、完成状态、目标异常及关键计数，不凭字段名称猜编码。
4. 从真实原程序缩到可独立触发的窗口，再控制规模、布局、依赖或门限；每次结论都限定到被测变量。
5. 重启前备齐输入、独立expected、符号与packet检查、采集和停止分支；实卡逐项执行，异常停止。
6. 将“指令定位”“机制确认”“生产修复”“完整程序验收”分别给出证据。

这次还留下了几条尤其容易忽略的经验：

- **软件字段宽度不等于硬件有效位宽。** 地址、store宽度和读回位型要分别检查。
- **指令条数少不等于硬件工作少。** 一条descriptor可以包含数万次小搬运，减少发射条数可能把工作集中到一条过长的指令里。
- **输出正确不等于执行健康。** watchdog可以报告异常，而搬运继续完成；return code、数值、guard和故障事件要分别判定。
- **事后读不到异常，不代表期间没有异常。** 首次事件快照比退出后的单次寄存器读取更有说服力。
- **插桩会改变时序。** 已通过的16段GS虽然没有中间join，但采样间隙使每条在下一条发射前自然完成；这不能代替生产紧密发射验证。
- **同宽位型载体与算术dtype是两回事。** 调试也必须沿用实际指令定义，不能为了方便而擅自换类型。

## 6. 结案边界与后续修复

本次证据可以确认的范围是：这条小颗粒GS能独立触发TDMA；触发与LSU timeout门限具有因果关系；
当前寄存器只保留低16位。此前考虑的“必须连续调用”“必须有前置CT”“达到65,536次才溢出”
都不是这一复现的必要条件。这些判断分别对应硬件事实文档中的`board-observed`及对本复现的排除结论。

精确watchdog时钟、stall和重载规则、配置的reset/初始化来源仍是`unknown`。
它们不影响已取得的触发机制结论，也不应继续成为迟迟不进入修复的理由。
但是，不能把当前板卡的字段行为外推为所有硬件版本的内部实现，也不能把本次可完成的fatal外推为解释了所有历史永久卡死。

生产修复应减少单条小颗粒GS的持续工作：在保持真实地址关系和dtype的前提下，考察能否合并连续搬运，
或改为等价的多条指令。具体方案必须验证连续发射、直接消费者和原attention，
不能直接把本次通过的4,096或16,384次写成通用硬件合法性上限，也不能把诊断用join推广到生产。

后续修复现已完成本轮实卡验收：统一Instr连续合并与有序分段后，原65,536次搬运变成4条紧密GS；
两种原布局、直接Sub/Exp消费者以及原4K、28-head attention的FP16/BF16都通过完整数值、guard与正常退出，未出现TDMA fatal。
consumer中的`0x5000`按SDK位定义单列为CT浮点状态，纠正了采集器“任意非零状态即失败”的误判，没有改硬件异常配置。
这闭合了本次GS问题的“定位→因果→通用修复→原程序验收”，完整产品矩阵和未知硬件细节仍保持各自边界。

这次积累的价值，是在缺少完整硬件资料时，仍能用实际二进制、主动采集和可区分假设的实验，
把“某个Tile超时”变成一条可复现、可解释、能指导修复的硬件约束。
