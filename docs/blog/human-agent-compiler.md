# 我们怎样用 Agent 做成一个加速器编译器

*从任务组织、架构重构，到自动 spatial/temporal mapping 与 LLaMA block 实卡优化*

> 初稿 · 2026-09-10。本文记录人—agent 协作的开发过程。实现复盘参考已提交代码至 `ba976c5a`；设备性能对应文中链接的具体实验产物，不代表后续修改均已完成板端复验。

一个完整的 LLaMA block 在真实芯片上算出了正确结果，接下来该做什么？

在我们的项目里，答案是打开 profile，继续追问：它为什么还需要一百多毫秒？

第一轮，我们发现空间划分让不同 Tile 重复读取了大量权重。修改生成逻辑后，程序明显变快，却在第一次实测中输出了满屏 NaN。修复新切分暴露的初始化错误、重新通过数值验收后，耗时降到约 37 毫秒。第二轮 profile 又把问题指向了数千次细碎的数据搬运和标量累加。继续追到指令生成，修正原生归约的选择规则，耗时进一步降到约 17.7 毫秒。

这是同一输入、同一设备会话下的单次阶段观测，还不是稳定 benchmark。但它已经提供了一条完整的工程线索：**观察设备行为，回到编译器里的生成原因，修改通用机制，再让真实程序检验它。**

这些工作是我与编程 agent 一起推进的。Agent 参与了调研、设计、实现、测试和定位；我也不断调整目标、质疑方案、讨论抽象，并检查它的结论究竟有多少证据。过程中有不少重构，也有错误判断、无效尝试和推翻重来的时刻。

这篇文章想讲的，就是这套协作方式怎样逐渐形成。编译器是贯穿全文的真实工程案例；即使你不熟悉数据流芯片，也可以从中找到几个更普遍的问题：怎样把任务交给 agent，怎样让它持续推进，什么时候需要介入，以及怎样知道事情真的做成了。

## 1. 先说清楚，我们在做什么

Wafer Compiler 的目标，是把高层张量程序编译为单卡多 Tile 设备上的可执行程序。

可以先把 Tile 理解为芯片上的一个计算单元。面对一个矩阵乘法、归约或者 attention，编译器不仅要决定使用哪些指令，还要回答：

- 哪一部分工作交给哪个 Tile？这属于 **spatial mapping，空间划分与映射**。
- 每个 Tile 内怎样切块、组织循环、复用数据和融合计算？这属于 **temporal tiling 与 fusion**。
- 中间结果放在哪里，什么时候搬运，下一位消费者什么时候可以安全读取？这涉及布局、存储、通信与完成关系。

在已经支持的图语义和硬件原语范围内，用户提供 PyTorch/XLA 导出的 StableHLO 张量程序，不需要为每个输入手写 kernel，也不需要手工给出上述映射。编译器完成这些工作，再通过 runtime 把产物交给设备执行。

文中会反复出现 IR，即编译器的中间表示。可以把它理解为编译过程中描述程序计算、数据和依赖的结构化形式；每个阶段都能检查和修改自己负责的那一层表示。

这并不意味着底层原语和 ABI 可以凭空出现。我们仍然需要理解设备指令，定义其语义与约束，实现目标转换和运行时适配。我们复用了 MLIR、XLA、`egg` 等基础设施，并在其上设计和实现面向该设备的编译栈。这里的“从零构建”，指的是目标编译体系与集成链路，不是重写所有基础库。

还有一个容易混淆的地方：**agent 在开发环中，编译器在产品执行链中。** Agent 修改的是编译器的能力；用户之后编译和运行一份受支持的程序，不需要每次再请一个语言模型替它安排算子。

### 与公开的 agent compiler 项目有什么不同？

Anthropic 的 C compiler 实验展示了多 agent 长时间推进复杂实现的能力。它的官方文章也记录了人的重要工作：构建测试环境、改进反馈方式，以及在 Linux 编译遇到瓶颈后引入 GCC 对照来拆分问题。[官方文章](https://www.anthropic.com/engineering/building-c-compiler)

Kimi 的 MiniTriton 则展示了从 DSL、MLIR 到 PTX/runtime 的完整系统，并报告了 nanoGPT 训练结果。其仓库明确注明维护者参与工程指导和审查，也说明了沿用 Triton 编程模型以及 kernel 调度方面的限制。[官方介绍](https://www.kimi.com/en/blog/kimi-k3)、[项目说明](https://github.com/MoonshotAI/minitriton)

对我们来说，值得研究的区别在于：输入是高层计算图，目标是需要显式管理多 Tile 工作和数据流的加速器，而目标执行合同也需要逐步查证和建立。

PyTorch 可以告诉我们数学结果应该是什么，却不会告诉我们芯片上正确的缓冲布局、异步资源生命周期和跨 Tile 完成协议应该怎样实现。**数学参考存在，目标执行模型仍然需要工程工作。**

这是一种不同的协作任务。没有必要通过猜测模型见过哪些训练代码，来解释双方项目的难度；更有价值的是把可用参照、输入层级、实际自动化范围和验证方式摆出来。

## 2. 我们实际怎样使用 agent

我们的工作台，核心是一个能够读取仓库、修改文件和执行终端工具的编程 agent，加上项目代码、文档、构建、测试与设备反馈。

![人、agent、仓库与工程证据之间的协作循环](../images/human-agent-compiler-workflow.svg)

图中真正重要的是反馈方向。人不需要替 agent 指定每一个函数怎么写；agent 也不应该仅凭一段顺畅的解释宣布完成。双方的判断，都要落到可检查的工程结果上。

### 2.1 给它一个结果，而不只给一个动作

“优化一下”“做得通用一点”“把剩下的全部完成”，都是真实开发中很自然的表达。但这些话本身没有回答：优化什么，哪些行为必须保持，什么结果算完成。

我们后来逐渐把任务写成几项明确的信息：目标、输入、修改边界、直接消费者、验收条件，以及本轮不做什么。

下面是一份按实践整理的任务描述，不是开发对话的逐字转录：

```text
目标：降低一个已通过数值验收的程序的设备耗时。

先调查：区分设备 Primary、engine counter 和插桩 Trace，
        将热点追到当前 IR 及生成它的代码，列出证据与未知项。

修改边界：针对已确认根因修改通用生成机制；
          保持输入、数值验收策略和已有合法性约束。

验证：先检查直接受影响的 IR/单元测试，再做 fresh package/no-card；
      需要设备时，在约定范围内做完整数值与匹配性能复验。

交付：修改、测试结果、实际前后差异，以及仍未验证的部分。
      没有收益或出现退化，也要保留记录。
```

这并不是要求每个小改动都先写长计划。一个局部修复可能几句话就足够。只有当修改跨越 IR、内存或 runtime 边界时，才需要把关系展开。

任务描述的作用，是让 agent 知道自己可以独立解决哪些问题，也让我们拥有共同的完成标准。

### 2.2 要求先查事实，再给方案

Agent 很擅长根据熟悉的工程模式提出一个看起来完整的方案。这种能力很有用，但在陌生硬件上，最需要警惕的恰好是那些没有明确来源的熟悉感。

例如，函数名里有 send，不代表此时已经发出了传输；两个算子属于不同 engine，不代表它们一定能够安全重叠；看起来只需要两个 buffer，也不代表真正生成的程序只有两个 allocation。

因此，开始一项跨层工作时，我们会让 agent 先回答三个问题：当前输入是什么，代码实际产生了什么，谁会直接消费这个结果。涉及硬件行为时，还要指出依据来自文档、实现还是本次实验。

这些问题并不直接提供答案，却能暴露方案是否建立在真实对象上。Agent 可以继续自主调研和实现，但不能把未确认的假设悄悄变成下游事实。

### 2.3 按可验证边界交付，而不是按文件数交付

编译器里的一个行为经常跨越很多文件：op 定义、verifier、lowering、CRT、runtime、模型和测试可能都要同步。一个“很小的 diff”未必完成了工作，一个较大的 diff 也未必意味着越界。

我们更关心的是，这次修改能否形成一个完整、职责一致的边界。例如，新增一种实际完成关系，既要在 IR 里表达，也要让目标代码真正发出它，让模型理解它，让缺少该关系的负例失败。

在这类任务里，agent 的实现能力确实提供了很大帮助：它能够沿着直接调用链检查多个 producer 和 consumer，并把定义、实现和测试一起更新。人的介入重点则是判断这套关系是否应该这样定义，而不是逐文件派发编辑指令。

### 2.4 自主推进需要明确的停止条件

局部 API 用法、代码路径和测试注册，能从仓库确定的就让 agent 自行处理。相反，改变数值语义、引入新的事实表示、扩大设备实验范围，或者需要未知硬件行为才能继续时，应当停下来讨论。

这能避免两种消耗：一种是每走一步都询问，让人变成执行按钮；另一种是把一句宽泛授权理解成可以不断改变目标和实现路线。

我们在这两端都走偏过。后来约束逐渐清楚：坚持完成结果，不等于拥有无限的修改范围；自主工作，也不等于隐藏需要人判断的取舍。

## 3. 长期项目的上下文，怎样留在工程里

这个项目跨过了很多轮会话。Git 历史能追到 5 月的设计与骨架、7 月的架构重基线、8 月下旬的集中重构，以及 9 月的实卡验证与优化。它并不是一个持续在线、从未丢失上下文的单次生成过程。

要让下一轮协作继续推进，我们需要把必要信息留在项目中。

| 工件 | 保存什么 | 下一轮怎样使用 |
| --- | --- | --- |
| `AGENTS.md` | 长期协作流程与工程约束 | 开始工作时读取，明确行为边界 |
| 编号设计文档 | 当前有效的语义、接口和职责 | 判断方案应当修改哪个边界 |
| `tasks/progress.md` | 当前状态和直接前置 | 找到正在推进的工作，而非重新猜优先级 |
| 当前实施计划 | 具体步骤、覆盖矩阵和验收 | 继续一个未完成任务 |
| `memory/` | 已验证的常见根因和调试方法 | 避免重复犯同一类错误 |
| Git 与实验记录 | 发生过什么、测量对应什么产物 | 比较、回退和复盘 |

这些文件不是模型的永久记忆。它们需要被主动读取、正确更新，并且保持不同职责。把所有东西都塞进一个超长说明，反而会让当前事实和历史方案难以区分。

### 文档既可能帮助，也可能制造惯性

我们曾经积累过很长的计划和很多看起来有道理的对象。问题在于，一旦某个对象写进正式文档，后续会话就容易把它当成既定架构，即使它还没有生产实现或直接消费者。

后来收缩文档时，又出现了相反的问题：未完成任务的具体交接合同被当成重复内容移到历史归档，当前计划只剩标题和覆盖矩阵。新一轮 agent 仍然无法仅凭当前文档决定怎样实现。[相关根因记录](../../memory/bugs.md)

这让我们对“上下文管理”的理解变得更具体：保留的不是尽可能多的文字，而是下一轮真正需要做决定的信息。当前合同必须足够明确；已放弃的方案则必须清楚地退出当前事实源。

### 一轮结束时，要留下能继续工作的交接

有效的交接通常只需要回答：完成到了哪个边界，哪些检查实际执行了，哪个假设被证伪了，下一步缺什么。

如果一次实验没有收益，就留下没有收益的证据；如果某个问题还只是热点线索，就不要在摘要里写成已经确定的根因。否则下一轮会在前一轮的过度总结上继续放大偏差。

我们也没有把提交数量或代码行数当作效率指标。现有记录能支持版本演化和实验复盘，却不足以给出统一的人力工时、token 成本或生产率倍数。讨论 agent 的价值时，应当区分已经观察到的能力和尚未统计的投入。

## 4. 它说完成了，我们怎样判断？

这可能是整个协作中最难的一部分。

Agent 能够写实现，也能够写与实现配套的测试和说明。如果三者使用了同一个错误假设，它们仍然可能互相吻合。

### 4.1 绿色测试也有自己的范围

2026 年 7 月的一次架构审计，重新检查了当时的真实 pipeline。局部门禁已经大量通过，但审计仍发现了重要缺口：candidate commit 只保留首个代表 Tile，target lowering 将结构化控制流按遍历顺序展开，以及没有闭合的完整生产入口。[审计记录](../../tasks/archive/12-architecture-evidence-reset.md)

这些问题不是给失败测试补一条判断就能概括的。它们说明，当时的测试没有覆盖真正需要交付的行为。

之后，我们更明确地区分了几层证据：

- verifier 检查当前 IR 是否满足自身合同；
- 单元与变换测试检查一个机制的具体行为；
- 功能数值模型检查支持范围内的执行语义；
- no-card 检查 package 和调用计划，但不执行设备算术；
- 实卡结果检验该产物在对应设备与输入上的行为；
- 匹配的设备计时，才回答性能有没有变化。

测试本身也需要检查：成功断言是否真的观察输出，故障注入能否使它失败，reference 是否与待测实现共享了同一错误。John Regehr 对 agent 生成的 C compiler 做独立测试时，也曾因相信一份生成的测试脚本而修正最初的结论。这是很直接的提醒：验证工具本身也需要被验证。[独立测试复盘](https://john.regehr.org/writing/claude_c_compiler.html)

### 4.2 什么时候应该停止修补，重新审查抽象？

有一段时间，我要求 agent review 编译器，希望它判断模块、算法和抽象是否足够合理、通用和高效。它最初却更倾向于沿现有实现找局部问题。

那类 review 当然也有价值，但没有回答我真正关心的问题。后来讨论逐渐转向：为什么 FA/FD 被视为某种特殊 fast path？为什么通用 collective 算法与特定 transport 绑在一起？新的优化是不是又引入了另一套描述未来 IR 的 shadow plan？

这些追问没有直接给出实现，却迫使我们重新检查问题的定义。

当同类问题反复出现、多个阶段各自维护一份相似事实，或者增加一种输入总要再补一层特判时，就值得暂停局部推进。此时，人的作用是把讨论从“这个 case 怎么过”提升到“哪个共同约束没有被表达”；agent 则继续承担查证、比较方案和实施重构的工作。

### 4.3 也要允许推翻人的要求

从人的一侧看，目标表达和验收方式同样需要反省。“通用”“最优”“高效”并不是一组自动相容的要求，更没有替 agent 定义取舍。

例如，一个合法程序是否必须等待 layout solver 证明全局最优才能交付？如果我们把优化偏好写成正确性门槛，agent 可能花大量工作维护这个要求，而整个产品迟迟无法前进。

因此，人不能只要求 agent 为自己的偏好补实现。方案比较应该允许它指出要求之间的冲突；发生争议时，我们一起明确哪些是语义硬约束，哪些是目标，哪些只是当前预算。

### 4.4 验证成本也是工程成本

我们还经历过另一类问题：为了证明修改有效，反复启动重型模型，结果大量时间花在等待和重新定位上。

后来形成的执行顺序是，先让直接受影响的单元与 IR 检查给出快速反馈，再通过真实规模的直接下游，最后集中运行必要的完整模型与设备实验。小复现负责定位，真实规模负责暴露容量、循环、tail 和规模行为；两者不能互相替代。

性能工作也一样。2026-09-06 的一次候选排序调整有明确的回退提交 `e54cde0c`；随后工作回到阶段计时与实际工作量观测。一些分析复用虽然通过了回归，却没有带来超出波动的明显加速。这些结果提醒我们，修改看起来更高效，不等于已经改善了瓶颈。

## 5. 协作怎样改变了编译器的设计

这些工程规则最终要落在具体系统上。Wafer Compiler 里，几类设计选择尤其体现了两者之间的联系。

### 5.1 用共享的索引语义连接不同阶段

一个 tensor reshape 或 transpose，在图层是访问关系，在空间划分后决定 producer 需求，在 temporal fusion 中又影响切块怎样向前传播。如果每层都靠自己的形状模式重新理解它，就很容易产生不一致。

我们使用基于 MLIR 的索引关系分析，在相应 current IR 上解释这些关系。普通纯图中的等价表示进入有界 e-graph 归一化；spatial demand 和 temporal fusion 则复用相应的索引语义，决定数据需求与合法变换。[索引关系接口](../../include/Wafer/Analysis/Linalg/IndexRelation.h)、[归一化设计](../../tasks/05-local-compute-normalization.md)

e-graph 的价值在于，在明确支持的语言内把相关等价式放入同一个探索问题，减少改写顺序对结果的影响。它不负责所有编译决策，也不将内部 e-class 或提取历史传给后续物理阶段。

这类抽象的价值，不只体现在某一条优化上。它也减少了人和 agent 在不同模块之间反复解释同一个概念的成本。

### 5.2 先落实空间结构，再组织 Tile 内执行

Spatial 决定怎样划分迭代域、把工作放到哪些 Tile，以及怎样形成 region；temporal 则从物化后的实际操作出发，决定 Tile 内的切块、循环和 producer fusion。

Region/grouping 与 fusion 不是同一个按钮。哪些操作被放在同一执行范围内，是一个问题；producer 是否能够沿 consumer 的需求进入同一个循环，是另一个需要 SSA、索引和 effect 证据的问题。

Tile 级 IR 让这些选择有了可检查的落点：不同 Tile 的工作、真实循环、buffer、view 和 movement 都明确存在。随后才生成指令，并处理 worker、order、completion 与实际内存规划。

FlashAttention 和 FlashDecoding 也沿这条体系接入。识别到的 attention 语义通过 online state、空间 contribution/merge 与局部 tiling 展开，再降低为普通计算和数据移动。这让算法支持与具体芯片传输实现保持分层，而不是把某个模型名称变成代码路径。

跨 Tile 数据交换也有自己的选择空间。对已支持的边界，编译器构造 DDR 或 peer movement 候选；collective 的参与者、数据与合并语义则先于 Ring、recursive doubling 等具体算法的物化。目标后端消费已经存在的数据流，而不是让应用开发者为每种划分手写通信协议。[通信设计](../../tasks/13-communication.md)

### 5.3 优化问题要与实际物化结果一致

PBQP layout 是一个典型例子。它把当前 value/use 的 layout 选择、consumer 约束、alias 和共享 conversion 表达成一个局部优化问题，目标关注实际布局物化的开销。

这里最容易出错的不是 solver 的名称，而是问题有没有建对：DPS destination 与 result 是否属于同一存储关系？多个 use 共享一次 conversion，是否被重复计费？solver 选中的 layout，实际 bufferization 是否采用了它？

当前实现还区分 `Optimal`、`Feasible`、`NoSolution` 与预算不足等结果。存在经过验证的完整合法 assignment 时，预算耗尽可以返回 `Feasible`，但不能把它称为已证明最优。[Solver 合同](../../lib/Wafer/Planning/PhysicalDataflow/ExactPBQPSolver.h)

PBQP 是每个实际候选内的 layout 子问题。外层联合选择协调 spatial、region、temporal、movement 等决策，并在已物化候选上比较结果；它不是把所有维度摊平成一个保证全局最优的无限搜索。

### 5.4 Current IR 是双方都能检查的事实

几轮重构后逐渐明确的一条关键原则是：选择可以先存在，但选择造成的程序事实必须进入实际 IR，才能交给下游判断。

```text
current IR → 选择 → 实际变换 → verifier → fresh analysis
```

例如，SPM 是容量有限、需要显式管理的片上存储。一个 buffer 的生命周期，必须由实际 allocation、alias、effect 和 completion 决定。估算可以帮助排序，却不能替代真正的内存规划。

候选失败后，销毁该候选；成功候选保留同一 owner 进入交付。这样，后面的 allocator、lowering 和 runtime 不需要再猜之前的计划“本来打算做什么”。

这条原则同时约束了编译器和协作过程：我们讨论的是同一份实际程序，而不是彼此看似吻合、实际已经分离的模型。[Physical-dataflow 合同](../../tasks/06-physical-dataflow-synthesis.md)

## 6. 一条完整现场：从 profile 到两轮实卡优化

前面的工作方式怎样实际发生？LLaMA block 的优化提供了一个足够具体的例子。

### 6.1 先固定实验对象和问题

对象是 LLaMA2-7B 配置的一个完整 decoder block：输入 `[1,16,4096]`，MLP 中间维度 11008，FP16，固定 seed 初始化输入和参数，使用实际 Hugging Face 层构造与 PyTorch eager reference。它不是整套 32 层网络的预训练推理。[输入构造](../../test/Board/PyTorch/wafer_pytorch_board_cases.py)

本组测量还保持了相同的未融合 attention 实现。因此，下面的收益不能归因于 FlashAttention 融合。

我们把计时分成三类：未插桩 production 的 Primary 设备事件时间，另一轮 Trace 中的 engine PMU，以及 Tile 本地的插桩周期。前者用于前后比较，后两者帮助定位。它们不能相加或互相相减来补出一个看似完整的耗时分解。

### 6.2 第一轮：为什么这么多时间在搬数据？

初始 profile 的 Primary 是 109.008003 ms。进一步看实际 IR，7 个 projection/MLP GEMM 都把 `M=16` 按行分给 16 个 Tile，每个 Tile 处理一行，却重复读取完整权重。

一个 `[4096,4096]` 的 FP16 权重矩阵是 32 MiB。16 个 Tile 各自读取一次，逻辑请求量就是 512 MiB。把所有权重与循环次数对账后，权重读取约占该版逻辑 DDR 读请求的 99.16%。这是指令请求量，不是 DRAM 总线的实测流量。

此时，优化任务已经从“让 LLaMA 更快”收窄为一个具体问题：空间 proposal 为什么偏向这种重复读取方式，能否根据当前 operand maps 构造更好的切分？

修改沿普通索引关系与 partition 传播机制实施，提出低重复读取的空间方案，并协调 consumer 和初始化 owner。预测访问量只用来产生 proposal，真正的候选仍要完整物化并通过后续验证。

### 6.3 第一次明显变快，却不能算成功

新切分的第一次 Primary 是 37.035999 ms，设备执行和采集模式都正常结束。但独立 PyTorch 比较发现：65,536 个输出全部是 NaN。

这份样本必须从有效性能对比中排除。Primary、Count 和 Trace 输出一致，只能证明三种运行模式一致；它们完全可能一致地算错。[失败样本](../data/board-performance/llama-spatial-failure-20260909.json)

回到实际指令，问题之一出现在初始化。新切分产生了一个每行 256 个元素、行跨度为 4096 的 view，旧 lowering 却把它当成连续的 4096 个元素一次填充。也就是说，它既遗漏了应初始化的位置，又写进了行间的空隙。

修复使用实际 stride 分解 logical fill，而不是为 LLaMA 增加一个特殊清零分支。相关检查验证每个目标恰好覆盖一次、空隙不被修改，再重新编译并做完整实卡验收。

通过数值比较后的 profile Primary 是 37.436001 ms。逻辑 DDR 读请求从 6,531,166,848 降到 474,011,200 bytes。这时，新的空间方案才形成有效的性能结果。[有效复验](../data/board-performance/llama-spatial-fill-20260909.json)

这里体现了一个重要边界：agent 可以非常快地推进一个有希望的优化；**是否允许把它记为成功，必须由独立结果决定。** 新优化还可能暴露旧实现没有走到过的错误，不能因为方向看起来正确就跳过修复。

### 6.4 第二轮：继续看剩下的时间，而不是沿用旧解释

第一轮之后，新的热点不再只是权重读取。Tile14 的 Trace 出现了 10,317 次 GatherScatter 和 8,434 次逐元素 add。显式 NCC join 只有 13 次，不能把整个控制开销都归因于同步。

沿调用追到两处 RMSNorm：每处在每个 Tile 上遍历 8 个 512 元素块，旧 lowering 把每块归约展开成逐项搬运和标量累加。两处就能解释 8192 次此类操作。

为什么没有使用硬件已有的 native reduction？选择门槛来自一个旧的编译展开预算，后来却被当成了实现偏好。它限制的是编译器愿意展开多少工作，并不是硬件原生归约何时更合适的证据。

修复删除了这个长度门槛，对满足既有 init、axis、dtype、rank 和 physical-result 合同的输入优先 native。不能满足合同的输入仍保持原有合法实现，并没有为了性能放宽硬件能力。

再次完整验证后，profile Primary 降到 17.677999 ms。Tile14 的 GS 调用降到 1,997 次，add 降到 178 次；DDR 请求量和 13 次 join 保持不变。结合消失的逐项循环，证据支持收益主要来自细碎归约指令及控制/提交开销的减少。[Native reduction 实验](../data/board-performance/llama-native-reduce-20260909.json)

### 6.5 结果怎样汇总，才不丢掉过程？

下面只使用同口径的 profile 流程中未插桩 Primary，每阶段各一个样本：

| 阶段 | Primary 设备时间 | 可核对的程序变化 |
| --- | ---: | --- |
| 初始 profile | 109.008003 ms | 按 M 切分，多个 Tile 重复读取权重 |
| 空间复用与 strided fill 修复后 | 37.436001 ms | 逻辑 DDR 读取约 6.53 GB → 0.474 GB |
| 合法归约优先 native | 17.677999 ms | Tile14 GS：10,317 → 1,997；add：8,434 → 178 |

三阶段输入 hash 与数值比较策略一致。65,536 个输出均通过完整 PyTorch 比较，使用 `rtol=0.002`、`atol=0.004`，记录中的最大绝对误差均为 0.00146484375。按这组观测计算，最后一阶段相对最初约为 **6.17×**，设备时间下降约 **83.8%**；这是特定产物与输入的阶段结果，不是稳定均值，也不代表完整 LLaMA 网络的加速比。

基线与各轮身份可从[初始 profile](../data/board-performance/llama-block-profile-20260909.json)、上述两个有效复验 JSON 及[性能记录](../board-performance-results.md)核对。首次全 NaN 的快速样本不在表中。

对 agent 协作而言，最值得复用的是这段过程：先拿到可解释的证据，再把任务收窄到共同生成机制；改动后重新判断数值和性能，新的瓶颈再触发下一轮调查。它不要求人预先知道最终该改哪一行，也不允许 agent 靠预想的收益跳过验收。

## 7. 同一轮工作，也有退化和未完成的部分

如果只展示上面的表，读者仍然看不到通用优化的另一半工作。

### Decode：一个程序的收益不能替另一个程序签字

Decode 的较早一轮优化，把单步 Primary 从 11.272 ms 降到 8.198 ms。Trace 指向远端归约状态的过早接收：本地计算尚未完成，就已经等待之后才需要的 maximum、sum 和 accumulator。修改将 receive 放到实际使用位置附近，同时处理共享 mask 访问，保留必要 wait，完整 PyTorch 和 KV prefix 检查通过。

但后续组合改动后的同类输入，Primary 又到了 11.443 ms，数值仍正确，性能却退化了。新的热点涉及 DDR acquire 和所选 partition，不能直接删除同步，也不能把 LLaMA block 的收益推广过来。[Decode 记录](../board-performance-results.md)

这种反例会改变后续任务。通用机制要接受其他消费者的检验，性能结论不能只选择最好看的一条路径。

### Prefill：从不可运行到可运行，不等于已经有加速比

4K、32-head prefill 曾因每 Tile 的完整 accumulator 占用 2 MiB 而无法通过实际 SPM 规划。只缩小计算块或改变最终输出写回，没有解决跨遍历保留完整状态的问题。

修复将归约状态 producer 与归一化 consumer 放进共同的输出 tile 遍历：每个输出 tile 完成全部 K/V recurrence 后立即归一化并写出。Accumulator 缩到 64 KiB，完整输出保存在 DDR。该输入最终完成 16,777,216 个元素的实卡 PyTorch 比较，单次 Primary 为 913.580017 ms。

修复前没有同配置设备基线，因此它证明了状态生命周期与可执行能力的改善，而不是一个设备加速比。该 case 的一次 Count 还发现事件数量超过 Trace 容量，因而没有启动 Trace；我们也不能据此补写一份不存在的完整热点分解。[Prefill 数据](../data/board-performance/prefill-local-state-20260909.json)

### 新的通用重构，还需要自己的设备证据

截至 `ba976c5a`，temporal 机制继续向通用实现收敛：为 fused producer 保留输出需求不能确定的内部归约参数，让 contraction、reduce、conv、view/shared chain 复用结果 tile 物化入口，并以 DPS/result maps 处理多结果状态。

该提交记录了 36 组实际 Instr/completion/SPM 正例和 11 个 fresh source→package→no-card case 的通过；它没有新增板端性能资格。新的融合 LLaMA 性能对比、Decode 退化和更充分的候选探索仍在推进。

编译器已经支持一些通信与 DDR 交换的自动选择，也不意味着所有可能的共享方案都被搜索过。例如，当时外部权重读入后再分发的候选尚未完整枚举，最终走 DDR 不能被解释成其他所有方案都已经输掉。

把这些边界写清楚，才能让下一轮 profile 真正提供新信息，而不是替上一轮总结背书。

## 8. 从这次项目里，我们能带走什么？

如果明天重新开始一个面向新硬件的 compiler 项目，我会先准备几样东西：一个真实输入、独立的数值 reference、能够运行的构建与检查命令、一份最小目标执行合同，以及当前任务的明确边界。

有了这些，再让 agent 持续推进。具体来说，有六条经验值得保留。

**第一，先建立可以纠正双方判断的反馈。** 一个系统越陌生，越不能只依赖熟悉的实现模式。文档、代码、模型和板卡各提供不同证据，存在分歧时要回到具体行为。

**第二，按可验证边界拆任务。** Agent 可以承担跨很多文件的实现，前提是输入、输出和消费者清楚。把工作拆成一百个文件编辑命令，未必比一个职责完整的任务更容易成功。

**第三，审查问题的建模，而不只是代码。** e-graph 的语言、PBQP 的变量与成本、search 的候选域都可能建错。人的技术判断与 agent 的调研能力，应当在这一层发生真正的合作。

**第四，把上下文作为工程工件维护。** 当前合同、任务状态和历史记录要能区分；一次失败之后，保留能帮助下一轮判断的最小经验。规则应服务于已知风险，也需要随着实现演进复审。

**第五，让“未知、失败、无收益”成为正常结果。** 预算耗尽不等于无解；运行结束不等于数值正确；局部改动通过测试不等于加速；一个模型变快不等于所有模型都变快。把这些区别保留下来，agent 才有可能据此选择正确的下一步。

**第六，管理验证与探索成本。** 快速复现、真实规模回归、完整模型和设备实验各有用途。有效的自主推进需要资源边界、停止条件和清晰交接，而不只是不断重复“继续”。

这次项目展示了 agent 可以参与到多深的系统开发：从优化问题的表达，到跨阶段实现，再到真实硬件上的定位和复验。它也展示了能力的条件——目标不清、事实缺失、反馈失真时，生成更多代码并不会自动让系统收敛。

完整 LLaMA block 跑通，是一个重要节点。之后的性能迭代继续检验编译器，也继续检验我们的协作方式。

**我们最终学到的，是怎样共同把一个模糊目标，变成可运行、可检查、可以被证据推翻并继续改进的工程过程。**
